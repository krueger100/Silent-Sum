## 1. FileCipher — `SSV1` authenticated blob container

### 1.1 Constants
| Name | Value |
|---|---|
| `magic` | 4 bytes `0x53 0x53 0x56 0x31` = ASCII `SSV1` |
| `version` | `1` (one byte) |
| `headerLength` | `6` |
| `nonceLength` | `24` |
| `macLength` | `16` |
| `overhead` | `46` (= 6 + 24 + 16) |
| default `isolateThresholdBytes` | `262144` (256 KiB) — constructor parameter, production uses the default; tests use 1 MiB |

### 1.2 Byte layout (fixed offsets, no length fields, no padding)
| Offset | Length | Content |
|---|---|---|
| 0 | 4 | magic `SSV1` |
| 4 | 1 | format version, always `0x01` |
| 5 | 1 | key id = `VaultKeyId.code` (see 1.3) |
| 6 | 24 | XChaCha20 nonce, fresh random per blob (CSPRNG, generated by the cipher's `newNonce()`) |
| 30 | n | ciphertext (same length as plaintext; n may be 0) |
| 30+n | 16 | Poly1305 tag |
Total length = plaintext length + 46. A 46-byte blob is a valid encryption of an empty plaintext.

### 1.3 Key ids (from `VaultKeyId` enum in vault_keys.dart)
| Enum name (`.name`) | `code` byte | HKDF `info` string | Purpose |
|---|---|---|---|
| `photo` | `1` | `silentsum/photo/v1` | full-size image blobs `photos/<id>.enc` |
| `thumb` | `2` | `silentsum/thumb/v1` | thumbnail blobs `thumbs/<id>.enc` |
| `manifest` | `3` | `silentsum/index/v1` | encrypted JSON index `index.enc` (note: enum name is `manifest`, info string says `index`) |
`VaultKeyId.fromCode(int)` returns the enum for 1/2/3 and `null` for anything else. The 32-byte key passed to FileCipher for id X is `HKDF-SHA256(ikm = 32-byte VMK, salt = empty, info = utf8(info string), L = 32)` (derived in `VaultKeys.derive`; the master key itself is never used for file encryption).

### 1.4 AEAD
- Algorithm: XChaCha20-Poly1305 AEAD exactly as in draft-irtf-cfrg-xchacha / libsodium `crypto_aead_xchacha20poly1305_ietf`: `subkey = HChaCha20(key, nonce[0..16])`; then RFC 8439 ChaCha20-Poly1305 with 12-byte nonce = `00 00 00 00 || nonce[16..24]`; 32-byte key; 16-byte tag. A React Native implementation using libsodium's `crypto_aead_xchacha20poly1305_ietf_encrypt_detached(plain, aad, nonce, key)` produces byte-identical ciphertext and tag.
- AAD = exactly the 6 header bytes: `53 53 56 31 01 <keyId>`. On encrypt the header is built from the requested key id; on decrypt the AAD is the first 6 bytes of the blob as stored (they have already been validated to equal the expected header).
- Output = `header(6) || nonce(24) || ciphertext || tag(16)` (concatenated with `concatBytes`).

### 1.5 `encrypt(plain, key, id)` algorithm
1. Build header `[0x53,0x53,0x56,0x31, 0x01, id.code]`.
2. Generate 24 random nonce bytes (CSPRNG).
3. AEAD-encrypt `plain` under `key` with that nonce and AAD = header.
4. Return concatenation per 1.4. If `plain.length >= isolateThresholdBytes` the work runs on a background isolate (`compute`); result is identical either way (pure performance concern — in RN do the crypto natively/off the JS thread).
5. No validation of key length is performed by FileCipher itself (the underlying algorithm requires 32 bytes and throws an ArgumentError otherwise).

### 1.6 `decrypt(blob, key, id)` algorithm and error contract
1. `parseHeader(blob)` (synchronously, before any async work):
   a. if `blob.length < 46` → throw `FileCipherFormatException('blob too short')`
   b. if bytes 0..3 != `SSV1` → throw `FileCipherFormatException('bad magic')`
   c. if `blob[4] != 1` → throw `FileCipherFormatException('unsupported version <blob[4]>')` (decimal, e.g. `unsupported version 9`)
   d. if `VaultKeyId.fromCode(blob[5]) == null` → throw `FileCipherFormatException('unknown key id <blob[5]>')`
2. If parsed key id != requested `id` → throw `FileCipherFormatException('blob was encrypted for <header.keyId.name>, not <id.name>')`, e.g. `blob was encrypted for thumb, not photo`. This happens BEFORE any decryption attempt (no key material touched).
3. Split: `header = blob[0..6]`, `nonce = blob[6..30]`, `cipherText = blob[30 .. len-16]`, `mac = blob[len-16 .. len]`.
4. AEAD-decrypt with AAD = header. On authentication failure (wrong key, flipped ciphertext bit, flipped tag bit, altered header bit that still parses, truncated-but-≥46-byte blob) the library error `SecretBoxAuthenticationError` is caught and rethrown as `WrongKeyException` (a detail-free exception, `toString() == 'WrongKeyException'`). Same isolate-threshold rule as encrypt (`blob.length >= threshold`).
5. Returns the plaintext as `Uint8List`.
Summary of error types:
| Condition | Exception |
|---|---|
| length < 46 | `FileCipherFormatException` (`blob too short`) |
| bad magic / version != 1 / key id not in {1,2,3} | `FileCipherFormatException` |
| key id valid but != requested | `FileCipherFormatException` (checked before decrypt) |
| wrong key, tampered body, tampered tag, truncation ≥ 46 bytes | `WrongKeyException` |
Timing note: format errors are thrown synchronously from `decrypt` (the Dart method is non-async), authentication failure is delivered as a failed Future. In TS, rejecting a Promise for all cases is acceptable; tests only assert the error type.

### 1.7 Static helpers
- `looksEncrypted(bytes)`: `false` if `length < 46`; `false` if bytes 0..3 != `SSV1`; else returns `bytes[4] == 1`. It does NOT validate the key-id byte (a blob with key id 7 "looks encrypted" but fails `parseHeader`).
- `parseHeader(blob)` → record `{keyId}` or throws as in 1.6 step 1.
- `FileCipherFormatException(message)`: `toString()` = `FileCipherFormatException: <message>`.

## 2. SecureDelete — best-effort overwrite-then-unlink
Constructor `SecureDelete({chunkSize = 65536, random})`. Default `random` = a FAST (non-secure) PRNG (`Random(seed)`) seeded with one secure 32-bit integer (`Random.secure().nextInt(1 << 32)`). Overwrite bytes only need to differ from the original, not be unpredictable.

`file(target)`:
1. If the file does not exist → return (no error).
2. try { `length = size`; if `length > 0`: open the file for writing WITHOUT truncation (Dart `FileMode.append`: O_RDWR|O_CREAT, no O_TRUNC, no O_APPEND — position is then explicitly set to 0), `setPosition(0)`, then loop: `n = min(remaining, chunkSize)`; fill the first `n` bytes of a reusable `chunkSize` buffer with `random.nextInt(256)` per byte; write those `n` bytes; `remaining -= n`. After the loop `flush()` (fsync). `close()` in a finally. } catch FileSystemException → ignored (read-only volume, race) and continue.
3. try `delete()`; catch FileSystemException → ignored (already gone).
Exactly ONE overwrite pass. Files of length 0 are just unlinked. Nothing is returned.

`directoryContents(dir)`:
1. If dir does not exist → return.
2. List the directory non-recursively, not following symlinks. For each entry: if it is a regular file → `file(entry)`; if it is a directory → recurse `directoryContents(entry)` then try to delete the (now empty) directory, ignoring FileSystemException. Other entity types (symlinks) are skipped.
3. The passed-in `dir` itself is NOT deleted; only its contents.

## 3. Atomic file write — `writeFileAtomically(target, bytes)`
1. Temp path = `<target.path>.<pid>.<seq>.tmp` where `<pid>` is the OS process id and `<seq>` is a process-wide counter starting at `0`, incremented on every call (e.g. `.../vault/index.enc.12345.0.tmp`, then `.1.tmp`, ...). Temp lives in the SAME directory as the target (so rename is same-filesystem).
2. Create the target's parent directory recursively (`mkdir -p`).
3. Open temp write-only (create/truncate), write all bytes, `flush()` (= fsync), `close()` in finally.
4. `rename(temp → target.path)` — replaces an existing target (POSIX rename; on Windows Dart uses MoveFileEx with replace). Result: after a crash the target is either the previous complete file or the new complete file.
5. No fsync of the parent directory; no cleanup of the temp file if step 3 throws (exception propagates, temp may remain). Call sites: photo/thumb blobs on import and restore, and `index.enc` on every index save.

## 4. VaultPaths — on-disk layout
- Production root: `<applicationSupportDirectory>/vault` (path_provider `getApplicationSupportDirectory()`; Android `files/` app-private dir, iOS `Library/Application Support`). Segments joined with the platform path separator.
- `root` = `Directory(root.path)`; `photos` = `<root>/photos`; `thumbs` = `<root>/thumbs`; `index` = `<root>/index.enc`; `photoFile(id)` = `<root>/photos/<id>.enc`; `thumbFile(id)` = `<root>/thumbs/<id>.enc`. `id` is a 32-char lowercase hex string (16 random bytes) produced elsewhere by `SecureRandomSource.hexId()`.
- `ensure()`: creates `photos` and `thumbs` recursively (thereby also `root`). Idempotent.
```
<root>/
  index.enc          FileCipher blob, key id 3 (manifest), JSON inside
  photos/<id>.enc    FileCipher blob, key id 1
  thumbs/<id>.enc    FileCipher blob, key id 2
```

## 5. SecureStore (platform keystore key/value)
Interface: `read(key) -> string|null`, `write(key, value)`, `delete(key)`, `containsKey(key)` (default: `read(key) != null`). Values are small strings (the JSON-encoded wrapped-VMK credential record and throttle state); the PIN is never stored.
Keys (`SecureStoreKeys`):
| Constant | Key string |
|---|---|
| `vaultCredentials` | `silentsum.vault.credentials.v1` |
| `throttleState` | `silentsum.vault.throttle.v1` |
| `all` | `[vaultCredentials, throttleState]` in that order — used by full reset to delete every key |

`InMemorySecureStore([initial map])`: plain Map; `snapshot` returns an unmodifiable copy; `containsKey` uses map membership (so a stored empty string counts as present).

`FlutterSecureStore([storage])` — pass-through to `flutter_secure_storage` 10.3.3 with these fixed options:
- Android: `AndroidOptions(resetOnError: false)` — values encrypted with an AES-GCM key held in the Android Keystore (hardware-backed where available), stored in app-private preferences. `resetOnError:false` means a keystore/decrypt failure throws to the caller instead of silently wiping stored values (never auto-erase the vault credentials).
- iOS: `IOSOptions(accessibility: first_unlock_this_device, synchronizable: false)` = `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not iCloud-Keychain-synced, never migrates to another device via backup/restore.
- `containsKey` delegates to the plugin's native containsKey. All errors propagate unchanged.
RN equivalent: react-native-keychain / expo-secure-store configured with the same accessibility and no synchronization; Android Keystore-backed; do not enable any "reset on error" behaviour.

## 7. Clock abstraction
- `Clock`: `now() -> DateTime` (wall clock, user-changeable) and `monotonic() -> Duration` (only moves forward within a process; security timeouts should prefer it).
- `SystemClock`: `now()` = `DateTime.now()`; `monotonic()` = elapsed time of a single process-wide Stopwatch started when the class is first touched (i.e. time since app start, unaffected by clock changes).
- `FakeClock([start])`: default start `2026-01-01 12:00:00` local; monotonic starts at `Duration.zero`. `advance(d)` adds `d` to both; `setNow(dateTime)` changes only the wall clock (simulates the user editing the date). Used by tests for auto-lock and throttling.
- Consumers: `VaultSessionController` (`unlockedAt = clock.now()`), `AppLifecycleGuard` (auto-lock timer, monotonic), cloud-backup screen (`lastBackupAt = clock.now()`), PinAuthService throttle.

## Tests

### test/core/security/file_cipher_test.dart
Fixtures: `cipher = FileCipher(isolateThresholdBytes: 1 MiB)`; `key` = 32 secure-random bytes; `jpegLike` = bytes `FF D8 FF E0` + utf8(`JFIF secret photo contents that must never appear on disk`) + 5000 bytes of `0x7A`. Helper `containsSequence(haystack, needle)` = naive substring search on byte lists.
1. `round trip small payload` — `encrypt(jpegLike, key, photo)` yields `blob.length == jpegLike.length + 46`; `decrypt(blob, key, photo)` equals `jpegLike` byte-for-byte.
2. `ciphertext hides the plaintext and starts with the SSV1 header` — `looksEncrypted(blob)` is true; `blob[0..4] == utf8('SSV1')`; `blob[5] == 1` (photo code); blob does not contain the byte sequence `FF D8 FF`; blob does not contain utf8(`secret photo`); `looksEncrypted(jpegLike)` is false.
3. `random nonce: same input encrypts differently every time` — two encryptions of the same plaintext/key/id are not equal.
4. `wrong key cannot decrypt` — decrypting with a different random 32-byte key throws `WrongKeyException`.
5. `wrong key id is rejected before decryption` — encrypt with `VaultKeyId.thumb`, decrypt requesting `VaultKeyId.photo` (correct key) throws `FileCipherFormatException`.
6. `tampering with body or tag fails authentication` — copy of blob with `blob[40] ^= 0x80` (a ciphertext byte, offset 30+10) throws `WrongKeyException`; copy with last byte `^= 0x01` (tag) throws `WrongKeyException`.
7. `malformed blobs are rejected` — `decrypt(10 zero bytes)` throws `FileCipherFormatException`; blob with `[0] = 0x00` (bad magic) throws `FileCipherFormatException`; blob with `[4] = 9` (bad version) throws `FileCipherFormatException`.
8. `large payload goes through the isolate path and round-trips` — 3 MiB of random bytes (above the 1 MiB threshold) encrypts and decrypts to identical length and content.

## UI flows

This subsystem has no screens of its own. UI-facing strings it owns:
- `AutoLockTimeout.label` values shown in the settings auto-lock picker, in this order: `Immediately`, `After 30 seconds`, `After 1 minute`, `After 5 minutes`, `After 15 minutes` (default selection `After 1 minute`).
- `AppInfo`: About screen title is `Calculator` while the app is in disguise mode, otherwise `SilentSum`; a list-tile subtitle reads `Version 0.1.0`; `0.1.0` is also passed as the application version to the open-source licenses page.
- `AppSettings.screenProtection` (default on) drives Android FLAG_SECURE while unlocked; `analyticsEnabled` (default off) and `crashReportsEnabled` (default on) drive the telemetry toggles; `onboardingDone` gates first-run onboarding; `backupEnabled`/`lastBackupAt` drive the cloud-backup screen (which sets `lastBackupAt = clock.now()` after enabling).
- Error messages from `FileCipherFormatException` (`blob too short`, `bad magic`, `unsupported version N`, `unknown key id N`, `blob was encrypted for X, not Y`) and `WrongKeyException` are developer-facing; they are not displayed verbatim to users.

## Security notes

- SSV1 binds magic+version+keyId as AAD, so a thumb blob cannot be decrypted as a photo and a re-versioned header fails authentication; it does NOT bind the photo id or file name, so two blobs under the same key can be swapped on disk/cloud without detection (documented limitation; a future `SSV2` would add the id to the AAD). Confidentiality is unaffected.
- Nonce: 192-bit random per blob, safe for random generation under one long-lived key; never reuse; never derive from a counter shared across devices/restores.
- Keys: per-purpose 32-byte HKDF-SHA256 subkeys (info `silentsum/photo/v1`, `silentsum/thumb/v1`, `silentsum/index/v1`, empty salt) of the VMK; FileCipher never sees the VMK. Keys are zeroed on lock in Dart (best-effort); in RN keep key material in native memory where possible and never in JS strings/logs.
- WrongKeyException deliberately carries no detail (wrong PIN, wrong key and tampering are indistinguishable to callers/logs).
- Interop: byte-identical to libsodium `crypto_aead_xchacha20poly1305_ietf_*_detached` with `ad = header`. Do not substitute AES-GCM or a different nonce size — existing vaults/cloud backups would become unreadable.
- SecureDelete is best-effort (single pseudo-random pass; flash wear-levelling may retain copies); its value is removing trivial undelete of ciphertext and of plugin temp files (camera/import plaintext). Overwrite failures are swallowed so unlink still happens; it never throws for missing files.
- Atomic write guarantees old-or-new file, never truncated; temp file name embeds pid+sequence to avoid collisions; parent dir is not fsynced and a failed write can leave a `.tmp` sibling.
- Vault lives under app-private Application Support (`.../vault`), never in Pictures/DCIM; Android `allowBackup=false` with data-extraction rules; iOS directory is currently included in iCloud/Finder backups (ciphertext only; the keychain item is device-only so a restored copy cannot be opened) — `isExcludedFromBackup` not yet set.
- Secure store: Android Keystore AES-GCM with `resetOnError:false` (a keystore failure must surface as an error, never silently wipe `silentsum.vault.credentials.v1`); iOS `AfterFirstUnlockThisDeviceOnly`, `synchronizable:false`. Only the wrapped-VMK record and throttle state live there; the PIN is never persisted anywhere.
- Settings are non-secret and stored in ordinary preferences; nothing security-relevant may depend on them (auto-lock duration is a policy input, not a secret). Defaults are privacy-preserving: analytics off, backup off, screen protection on.
- Clock: security timeouts (auto-lock, throttle) should use `monotonic()`, which cannot be shortened by editing the system clock; `now()` is only for display/persisted timestamps.

## Open questions

- Isolate threshold (256 KiB) exists only to keep Flutter's UI thread responsive; in React Native the crypto should run natively (libsodium/JSI) regardless of size — confirm whether the RN port wants to keep a configurable threshold for parity with tests (the test constructs FileCipher(isolateThresholdBytes: 1 MiB)).
- SecureDelete opens the file with Dart FileMode.append then seeks to 0; Dart implements 'append' as O_RDWR|O_CREAT without O_APPEND (position set to end after open), so the write overwrites in place. A port must open read/write WITHOUT truncation and WITHOUT O_APPEND (with O_APPEND the writes would be appended, doubling the file instead of overwriting).
- AppSettings equality uses Dart DateTime ==, which also compares the UTC/local flag; toJson always writes UTC, so a settings object created with a LOCAL lastBackupAt will not be == to its round-tripped copy. Decide whether the TS port normalises lastBackupAt to UTC (recommended) or reproduces this quirk.
- PrefsSettingsStore.load swallows only FormatException (invalid JSON); a valid non-object JSON value (e.g. a bare number) throws a TypeError that propagates. Decide whether the port should fall back to defaults for any decode failure.
- AppSettings.fromJson casts booleans with `as bool?` — a string 'true' would throw rather than fall back. Confirm strictness for the port.
- The atomic-file test asserts the absence of `<target>.tmp`, but the real temp name is `<target>.<pid>.<seq>.tmp`; the port's test should assert that no `*.tmp` sibling remains (and consider cleaning up the temp file when the write fails, which the Dart code does not do).
- Vault root is `<application support>/vault` via path_provider; on RN choose the equivalent app-private, non-media, backup-excluded directory (Android filesDir, iOS Library/Application Support) and also decide whether to set isExcludedFromBackup on iOS, which the Flutter app has not done yet.
- SharedPreferencesAsync stores `silentsum.settings.v1` without the legacy `flutter.` prefix (Android DataStore backend). If the RN app must read settings written by the Flutter app on the same device (unlikely for a rewrite), the storage backend would have to match; otherwise only the key name and JSON shape matter.
- SystemClock.monotonic() starts at first access of the class (Stopwatch started lazily), not at process start; only relative differences are used, so any monotonic source (performance.now()/SystemClock.elapsedRealtime) is acceptable.
- flutter_secure_storage 10.x on Android no longer offers the encryptedSharedPreferences option; the doc comment describes AES-GCM with a Keystore key over app-private preferences. Confirm the RN keychain library's Android backing (Keystore AES-GCM vs EncryptedSharedPreferences) is acceptable; there is no on-disk format compatibility requirement, only the semantics (no auto-reset, device-only).
